# 架构边界与集成说明

## 1. 当前推荐架构

当前仓库面向“新主链”开发时，统一按以下边界理解：

- `asset`
  - 设备、账号、位置、组织等主数据
- `device_api`
  - 设备采集
  - 协议适配
  - 结果标准化
  - 设备事实回写
- `workflow_center`
  - 工作流执行
  - 巡检写回
  - 库存与主机变量
  - 诊断查询
- `network_analysis`
  - 接口利用率
  - 地址定位
  - 分析型快照与统计

## 2. legacy 约束

- `automation` 只保留历史兼容与生产兜底职责
- 新能力默认不再进入 `automation`
- 新主链运行时不应依赖 `apps.automation.*` 的实现细节

## 3. `device_api` 标准化结果合同

### 3.1 标准集合

标准化采集结果统一写入：

- `plan_arp`
- `plan_mac`
- `plan_lldp`
- `plan_aggre_port`
- `plan_ip_interface`
- `plan_interface_brief`
- 其它类型统一遵循 `plan_<collection_type>` 命名

### 3.2 冻结字段

所有标准化结果必须保留以下字段：

- `hostip`
- `hostname`
- `idc_name`
- `log_time`
- `summary_plan_id`
- `plan_id`
- `collection_type`
- `collection_method`
- `execute_time`

允许补字段，但不允许删除、重命名或改变这些字段语义。

## 4. NetClaw-CN 对接边界

### 4.1 允许依赖

NetClaw-CN 当前及后续应优先依赖：

- `device_api` 稳定结果接口
- `workflow_center` 稳定工作流接口
- `network_analysis` 稳定分析接口
- `config_center` / `dcs_control` / `topology` 的稳定领域接口

### 4.2 禁止依赖

- `automation.CollectionPlan`
- `asset.NetworkDevice.plan`
- 原始 `plan_*` Mongo 表
- 在 NetClaw-CN 内重复维护厂商能力判断与分流逻辑

### 4.3 需审批项

以下事项必须先提方案再实施：

- 修改 `asset` 模型结构
- 改变已跑通接口的字段语义
- 破坏 NetClaw 现有稳定入口兼容性的改造

## 5. 迁移原则

### 5.1 原则

- 先建立新入口，再收缩旧入口
- 先保兼容，再做替换
- 新能力只进新主链

### 5.2 当前建议

优先理解并维护以下方向：

1. `device_api` 继续成为统一采集主链
2. `workflow_center` 承接工作流与巡检结果
3. `network_analysis` 承接分析快照
4. `automation` 逐步收缩为 legacy 兼容层
