# device_api 阶段性总结（2026-03-13）

## 1. 模块定位

`backend/apps/device_api/` 是网络设备数据采集能力的后端核心模块，主要承担以下职责：

- 管理采集方案，包含汇总方案 `DeviceCollectionPlans` 和子采集方案 `DeviceSubCollectionPlan`
- 维护多协议采集配置，目前模型层支持 `NETMIKO`、`NETCONF`、`SNMP`、`RESTCONF`、`Telemetry`
- 执行采集任务，支持南向驱动模式和本机直连模式
- 处理采集结果、字段映射、结果查询与详情下钻
- 对外提供采集方案、执行入口、结果列表、结果详情等接口

从业务上看，这个 app 连接了“方案配置 -> 执行采集 -> 原始结果落库 -> 前端结果展示”整条链路。

## 2. 今日完成的更新

### 2.1 协议能力与校验对齐

- 补齐序列化器对 `SNMP`、`RESTCONF`、`Telemetry` 字段的暴露与写入支持
- 创建、更新校验从“至少启用 Netmiko/Netconf 一种”扩展为“五种协议至少启用一种”
- 新增协议级最小校验：
  - `SNMP` 必须提供 `snmp_oids`
  - `RESTCONF` 必须提供 `restconf_endpoint`
  - `Telemetry` 必须提供 `telemetry_subscription_path`
- 进一步按当前后端真实能力收口 `RESTCONF`：仅允许 `GET`，避免前端可配置但执行层并不支持的错位

### 2.2 本机直连执行能力补齐

- `services_new.py` 中补充本机执行所需的设备信息构造，包括 `ssh/netconf/snmp` 相关能力字段
- 新增本机执行载荷构造逻辑，统一将方案配置转换为连接管理器可消费的数据结构
- `execute_both_collection_local()` 从原先只处理 `NETMIKO/NETCONF`，扩展为可返回：
  - `netmiko_result`
  - `netconf_result`
  - `snmp_result`
  - `restconf_result`
  - `telemetry_result`

### 2.3 执行入口与结果查询修正

- `views.py` 中执行参数校验已按五种协议重写
- 本机模式下允许 `SNMP/RESTCONF/Telemetry` 参与校验与执行
- 南向驱动模式下明确保留当前限制：仅支持 `NETMIKO/NETCONF`
- 执行接口响应补充 `snmp_result/restconf_result/telemetry_result`
- 结果列表支持 `summary_plan_id`、`sub_plan_id` 组合过滤
- 子结果详情支持按 `plan_id + device_ip + execute_time` 精确下钻，避免取到错误批次

### 2.4 测试与验证

- 新增并补强 `backend/apps/device_api/tests.py`
- 已验证：
  - `python3 -m py_compile backend/apps/device_api/*.py`
  - `python3 backend/manage.py test apps.device_api.tests -v 2`

## 3. 当前状态判断

目前 `device_api` 的模型层、序列化层、执行入口层和结果查询层，已经基本与前端现有交互对齐；其中“立即会出错”的协议错位问题已优先修复。

但需要注意，当前“支持”分为两层：

- 配置与接口层：五种协议都已能被识别和传递
- 实际执行层：
  - 本机直连已接入五种协议返回结构
  - 南向驱动仍只支持 `NETMIKO/NETCONF`
  - `RESTCONF` 当前后端执行逻辑实际只支持 `GET`

## 4. 后续仍需完善的内容

### 4.1 执行能力补全

- 南向驱动执行链路补齐 `SNMP`、`RESTCONF`、`Telemetry`
- 明确 `RESTCONF` 是否需要支持 `POST/PUT/DELETE`，若需要，应补齐连接管理器与服务层实现
- 明确 `Telemetry` 的设备连接配置来源，当前仍依赖较弱的占位配置

### 4.2 配置模型补强

- `RESTCONF` 当前仅有 `endpoint/method/path/mapping`，缺少请求头、认证、请求体等更完整配置
- `SNMP v3` 所需的认证与加密参数尚未在当前方案配置中完整体现
- 建议统一梳理“模型字段支持”和“运行时真实支持”之间的能力矩阵，避免再次出现协议名义支持但执行不通

### 4.3 结果与回归测试

- 为五种协议分别补充执行成功/失败的服务层测试
- 为结果过滤、结果详情精确查询补充更多接口测试
- 后续如继续调整前端，需要将前后端协议字段、执行方式、结果结构整理成固定接口契约文档

## 5. 建议的下一阶段工作

建议下一阶段优先级如下：

1. 完成南向驱动模式的多协议补齐或明确下线多余入口
2. 完整定义 `RESTCONF/Telemetry/SNMP v3` 的运行时配置结构
3. 增加执行链路自动化测试，减少协议扩展时再次出现前后端错位
