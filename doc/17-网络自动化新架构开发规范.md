# 网络自动化新架构开发规范

更新时间：2026-03-15

## 1. 目的

本规范用于约束 BasePlatform 在网络自动化新架构上的后续开发方式。

配套阅读：

- [16-device_api替代automation架构审视与迁移计划](./16-device_api替代automation架构审视与迁移计划.md)
- [18-legacy字段到新架构字段映射](./18-legacy字段到新架构字段映射.md)

这里的“新架构”特指：

- `device_api`：统一承载网络设备采集、协议适配、结果标准化、设备事实回写、能力画像。
- `workflow_center`：统一承载工作流执行、巡检写回、库存编排、主机变量、诊断与后续自动化领域服务。
- `network_analysis`：统一承载接口利用率分析、地址终极定位、后续分析型快照与统计能力。

`automation` 的定位只有两个：

1. 历史需求来源
2. 生产兜底链路

它不是新架构的实现基础设施，也不是新架构的可复用公共库。

---

## 2. 核心原则

### 2.1 以“新能力中心”而不是“旧功能搬家”为目标

新架构的目标不是把 `automation` 原封不动搬到新目录，而是围绕“更智能、更全面、更高效的网络自动化能力中心”重新设计。

因此后续开发必须满足：

- 新模块优先围绕领域职责建模，而不是围绕旧文件结构拆分。
- 新接口优先围绕稳定服务能力设计，而不是镜像旧 URL 和旧参数。
- 新数据模型优先表达业务语义，而不是保留历史随意命名。

### 2.2 `automation` 只能作为需求输入，不能作为运行时依赖

允许：

- 将 `automation` 的现有功能视为需求参考、行为参考、字段参考。
- 在一次性迁移命令、离线导入工具中读取 legacy 表数据。
- 在并跑比对阶段把 `automation` 的运行结果作为对照样本。

禁止：

- 在 `device_api`、`workflow_center` 的运行链路中 import `apps.automation.*`
- 复用 `automation` 的 service、task、tool、view、serializer、cache helper、processor、consumer
- 让新接口在执行时回调 `automation` 的 Python 实现
- 让新模型 proxy 到 `automation` 模型作为长期方案

结论：

- `automation` 是兜底，不是底座。

### 2.3 新链路必须独立可运行

每一项新能力都必须满足：

- 不依赖 `automation` 的代码即可单独执行
- 不要求 `automation` 先初始化某些中间状态
- 不通过“写回 legacy 表后再读 legacy 表”的方式完成主链路

如果某个功能只有在 `automation` 存在时才能运行，则该功能不算完成。

## 3. 架构边界

### 3.1 `device_api` 职责

只承载以下内容：

- 设备能力画像
- 设备与方案绑定
- 多协议采集执行
- 厂商/产品线适配
- 采集结果标准化
- 设备事实发现与回写
- 面向外部系统的稳定设备能力接口

不承载：

- 历史流程审批语义
- 与采集无关的通用流程编排
- 旧自动化任务的直接执行兼容层

### 3.2 `workflow_center` 职责

只承载以下内容：

- 工作流执行记录
- 巡检写回
- 主机变量与库存编排
- 诊断、统计、工作流侧查询接口

不承载：

- 网络设备原子采集逻辑
- 协议连接细节
- `automation` 原任务对象的直接镜像实现

### 3.3 `network_analysis` 职责

只承载以下内容：

- 接口利用率分析
- 地址终极定位
- 基于标准化采集结果的分析型快照
- 分析任务的重建、导出与查询接口
- `interface_used`、`tracking_main` 等 legacy 分析需求的替代实现

不承载：

- 原始设备采集
- 工作流编排
- 资产主数据维护

### 3.4 `automation` 职责

只承载：

- 旧链路继续可运行
- 生产兜底
- 并跑对照

不再承载：

- 新功能开发
- 新厂商适配
- 新协议支持
- 新接口定义
- 新数据模型设计

## 4. 设计约束

### 4.1 命名约束

新架构禁止保留明显历史痕迹命名，除非是一次性导入阶段的临时字段。

例如：

- 禁止在新模型中继续使用 `ans_name`、`ans_group_hosts`、`ans_memo` 这类历史字段名
- 应改为 `name`、`hosts`、`description`、`variables`、`object_name`、`created_at`

命名要求：

- 字段名必须能直接表达业务语义
- 不允许保留“当年随便取的名字”
- 同一领域对象在不同 app 中命名要统一

### 4.2 模型约束

新模型优先遵循以下规则：

- 主运行模型不允许 proxy legacy 模型作为长期设计
- 与 legacy 的映射关系只能作为迁移辅助字段，例如 `legacy_id`
- 领域模型需要有明确主键、唯一约束、索引和生命周期字段

### 4.3 接口约束

新接口设计遵循：

- 对外暴露的是稳定能力，不是内部表结构
- 支持版本化路径，如 `/v1/`
- 新接口参数命名必须使用新语义字段
- 不为了兼容 legacy 前端而把旧字段名继续暴露为主接口字段

如果需要兼容：

- 只能在兼容层做字段映射
- 不能污染主 serializer 和主模型

### 4.4 代码复用约束

允许复用：

- `utils/` 中与新架构语义一致的底层连接库、通用数据库工具、加解密工具、Mongo 工具

不允许复用：

- `automation/tools/`
- `automation/tasks.py`
- `automation/views.py`
- `automation/serializers.py`
- `automation/cache_utils.py`
- `automation/inspection.py`

如果旧逻辑确实有价值：

1. 先抽象出“它解决的业务问题”
2. 再在新模块中重新实现
3. 不做目录级复制粘贴

---

## 5. 迁移与导入规范

### 5.1 迁移工具允许读取 legacy 表，但只限离线命令

允许存在：

- `import_legacy_*`
- `export_legacy_*`
- `compare_legacy_*`

这些命令的要求：

- 只允许按物理表或只读 ORM 读取 legacy 数据
- 不允许成为运行主链路的一部分
- 必须支持幂等执行
- 必须支持 dry-run

### 5.2 并跑原则

新旧并跑时：

- 新链路独立执行
- 旧链路独立执行
- 结果在比对层汇总
- 不允许新链路调用旧链路完成业务处理

---

## 6. Review 检查清单

每次提交涉及新架构时，必须逐项自查：

- 是否新增了对 `apps.automation.*` 的运行时 import
- 是否把旧字段名直接搬进了新模型
- 是否只是把旧函数换了个目录
- 是否存在新链路写 legacy 表再读回来的行为
- 是否把兼容层逻辑混进了主模型或主 serializer
- 是否新增了清晰的测试来证明新能力独立可运行

如果任一项答案是“是”，默认不允许合并。

---

## 7. 完成定义

一个“替代 `automation` 的新能力”只有在满足以下条件时才算完成：

- 已在 `device_api` 或 `workflow_center` 中独立实现
- 运行时不依赖 `automation` 代码
- 命名、模型、接口符合新架构语义
- 已有单测或集成测试覆盖关键路径
- 已有 legacy 导入或并跑方案
- 已明确回滚方式

如果只是“功能看起来一样，但底层仍依赖 `automation`”，则不算完成。

---

## 8. 当前执行要求

从本规范生效起，BasePlatform 的网络自动化替代任务统一遵守以下执行口径：

- `automation` 视为生产兜底，不主动修改、不继续扩展
- 新功能只进入 `device_api` / `workflow_center`
- legacy 仅用于需求参照、数据导入、并跑比对
- 任何“新瓶装旧酒”式实现都视为不合格实现
