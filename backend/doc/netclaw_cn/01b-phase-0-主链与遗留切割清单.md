# Phase 0 附录 B：主链与遗留切割清单

## 1. 文档目的

本文件定义 NetClaw-CN 在 NetAxe backend 中的主链、兼容链、遗留链和非依据模块，防止后续研发继续把新能力回流到 legacy 模块。

## 2. 分类定义

| 分类 | 含义 | 允许动作 | 禁止动作 |
|---|---|---|---|
| 主链 | 后续 phase 的正式承接对象 | 新需求、重构、接口统一、测试补齐、前后端联动 | 无 |
| 主链支撑 | 为主链提供支撑能力，但不一定直接对外暴露 | 在产品化视角下演进 | 以历史实现惯性替代新主链设计 |
| 遗留兼容 | 仍被存量逻辑依赖，但不再承接新需求 | 兼容、回退、迁移、风险隔离 | 新增主链能力、扩大依赖面 |
| 非依据模块 | 本轮设计、实施、验收都不应作为依据 | 维持现状，必要时最小修复 | 作为 phase 架构依据或未来主链能力来源 |

## 3. 模块切割表

| 模块 | 分类 | Phase 0 处理原则 | 备注 |
|---|---|---|---|
| `device_api` | 主链 | 作为默认采集主链继续增强 | 国产设备优先走 NetAxe 原生能力 |
| `asset` | 主链 | 作为设备事实与关系底座继续增强 | 涉及模型变更需谨慎评审 |
| `workflow_center` | 主链 | 未来演进为统一执行中心 | 统一 `execution_query` 的主要承接者 |
| `network_analysis` | 主链 | 未来演进为网络智能中心 | 消费事实并输出分析结果 |
| `dcs_control` | 主链 | 未来演进为安全策略中心 | 安全审计与差异分析主承接 |
| `config_center` | 主链支撑 | 纳入产品化与前端联动设计 | 不以历史页面/接口形态限制新设计 |
| `api` | 主链支撑 | 纳入统一 agent API 和前端联动设计 | 作为统一入口支撑 |
| `topology` | 主链支撑 | 只保留可复用事实能力，冻结旧手工图主链地位 | 后续以事实拓扑为目标 |
| `automation` | 遗留兼容 | 冻结，不承接新需求 | 仅保留兼容、回退、迁移价值 |
| `monitor` | 非依据模块 | 不进入本轮设计、实施、验收依据 | 仅最小维护 |
| `support` | 非依据模块 | 不进入本轮设计、实施、验收依据 | 仅最小维护 |

## 4. 强制冻结规则

### 4.1 `automation`

冻结结论：

- `automation` 被正式定义为 legacy 模块
- 除兼容、回退、迁移外，不再承接任何新需求
- 任何新 agent 任务类型都不得直接设计在 `automation` 内实现

允许保留的价值：

- 作为存量运行链路的 fallback
- 作为数据迁移、回溯、对账对象
- 作为遗留模型兼容层

### 4.2 `monitor` 与 `support`

排除结论：

- 两者均不作为本轮架构、实现和验收的依据模块
- 后续若出现历史引用，只能作为现状说明，不得据此反推新主链设计

## 5. 必须显式登记的 legacy 依赖

### 5.1 `NetworkDevice.plan -> automation.CollectionPlan`

结论：

- 这是当前仓库已存在的 legacy 模型绑定
- 本依赖只允许作为兼容存量采集配置的桥接关系存在
- 不允许在 Phase 1 及之后继续扩大该依赖面
- 后续新主链采集方案以 `device_api` 父子方案模型为准

当前仓库证据：

- `backend/apps/asset/models.py` 中 `NetworkDevice.plan` 仍指向 `automation.CollectionPlan`
- `backend/apps/device_api/management/commands/sync_legacy_plan_bindings.py` 已体现新旧方案同步的过渡属性

### 5.2 旧 `topology` 手工图链路

结论：

- 当前 `topology` 仍存在 Mongo 手工图读写逻辑
- 该链路可作为现状兼容能力保留，但不能定义未来事实拓扑主链

当前仓库证据：

- `backend/apps/topology/views.py` 中仍直接操作 `Automation.topology` 集合

## 6. 主链准入规则

后续任一需求只有同时满足以下条件，才允许进入主链：

1. 能映射到四个领域中心之一。
2. 不新增对 `automation`、`monitor`、`support` 的设计级依赖。
3. 对外优先通过统一 agent API 暴露，而不是追加碎片化内部接口。
4. 若涉及设备执行或安全审计，必须考虑执行台账、证据和回滚引用。

## 7. 回滚与兼容原则

- Phase 0 只做架构定版，不移除存量 legacy 能力。
- 后续 phase 若主链切换失败，允许通过兼容层回退到 legacy 运行路径。
- 回退只允许回退“运行策略”，不允许把新功能直接补回 `automation`。

## 8. 已知限制

- 当前多个 app 仍直接或间接引用 `automation`；Phase 0 只完成定性和冻结，不在本阶段清除所有引用。
- `topology` 旧手工图链路仍在线，需在 Phase 3 前明确事实拓扑替代方案。
