# 数据预处理评估与设计方案

更新时间：2026-03-03

## 1. 目标

统一不同协议/厂商的原始采集结果，输出稳定的 `processed_data`，再写入按类型划分的 MongoDB 集合。

## 2. 当前实现（已落地）

### Layer 1：结构解析（processors）

- 入口：`apps/device_api/processors/`
- 派发键：`vendor + device_type + collection_type + method`
- 降级机制：支持 `device_type=''` 的通用注册，适配不同设备类型值

### Layer 2：厂商兜底规范化（tools）

- 入口：`apps/device_api/tools/`
- 触发条件：未命中处理器时兜底
- 适用场景：主要用于 Netmiko 路径的历史兼容

### Layer 3：元数据注入

- 入口：`apps/device_api/models_api.py` `inject_metadata`
- 注入字段：`hostip` / `hostname` / `idc_name` / `log_time`

### 标准字段补齐

- 字段来源：`apps/device_api/fields_mapping.py` `field_mapping`
- 行为：处理器结果在入库前按 `collection_type` 补齐标准字段缺省值

## 3. 本次关键调整

1. `resolve_raw_data` 主链路移除 `apply_field_mappings` 执行分支
2. `process_raw_data`（deprecated）不再执行字段映射，统一透传/处理器逻辑
3. 对 `NotImplementedError` 处理器做降级，不直接中断流程
4. NETCONF 无可用处理器时明确失败：`netconf_no_processor`

## 4. 现状评估

### 优势

- 处理链路职责清晰，入库前行为可预测
- 子方案不再强依赖字段映射配置，配置复杂度降低
- 标准字段定义集中在 `fields_mapping.py`，便于统一演进

### 待完善

- NETCONF 处理器覆盖率仍不足（H3C/Huawei 多个类型待补齐）
- 部分厂商处理器仅透传，规范化能力弱
- 缺少系统化单元测试验证字段完整性与格式一致性

## 5. 推荐下一步

1. 补齐 H3C/Huawei NETCONF TODO 处理器
2. 给 `resolve_raw_data` 增加协议/类型维度单测
3. 将子方案字段映射配置在前端降级为“高级兼容项”，默认折叠或隐藏
