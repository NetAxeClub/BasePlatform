# device_api 后续任务

## 1. 目标

本文件只保留 `device_api` 当前仍需持续推进的事项，不重复记录历史方案、评估过程和阶段性归档。

涉及“以 `device_api` 替代 `automation` 设备采集主链”的详细 phase 拆分、验收门禁和回退要求，见：

- [采集主链替代实施与验收清单](./采集主链替代实施与验收清单.md)

## 2. 当前优先级

### P0：已完成范围冻结

- `P0-范围冻结与切换门禁.md` 已冻结首批切换范围、延期范围和 fallback 门禁
- 灰度对比与回退演练阶段必须使用 `plan_collect_device_main(clear_history=False)`
- Telemetry 明确不计入当前主链替代通过项

### P1：主矩阵能力补齐

- 补全 Cisco / Ruijie / Hillstone / ZTE / Maipu / Mellanox / Centec 的标准化深度
- 把主矩阵厂商从“可采集”推进到“结果稳定且字段一致”
- 持续补厂商处理器和模板覆盖
- 使用 `audit_device_api_coverage` 输出未匹配画像、未绑定方案、缺账号、缺模板和缺执行方式清单
- 当前 P1 已完成，遗留 14 台例外设备见 `P1-画像与绑定覆盖报告.md`

### P1.5：CLI 画像与占位模板基线

- 先为各厂商补齐按设备类型区分的 CLI 命令画像，不再把“缺模板”默认处理为移出支持矩阵
- H3C、Huawei 需覆盖交换机 / 路由器 / 防火墙三类 CLI 基线
- 其它厂商至少建立一组基础 `show`/只读命令集
- 对缺失的 TextFSM 文件先创建空白占位模板，并同步补索引
- 审计报告要区分“模板不存在”和“模板存在但解析待补”

### P1：`tools/` 职责继续收窄

- 继续收敛为值规范化层
- 避免再承担结构解析或字段重命名职责
- 保持 `processors -> tools -> metadata` 的单一方向

### P1：结果链路验证

- 增加更多代表性样本回归
- 扩展 `collection-results/latest/` 的边界测试
- 持续验证标准合同字段 9 项齐全

## 3. 中期任务

### P2：Telemetry 能力

- 实现 Telemetry 真执行而不是占位
- 增加 Telemetry 结果标准化和回归测试

### P2：查询与性能

- 补采集结果查询接口性能测试
- 复核 Mongo 复合索引是否覆盖当前查询路径
- 持续收敛慢查询和无索引查询

### P2：与分析链路联调

- 持续验证 `network_analysis` 对标准化结果的消费稳定性
- 保证接口利用率、地址定位对 `device_api` 结果的依赖不回退到 legacy 表

## 4. 长期任务

### P3：legacy 收缩

- 持续把新增采集能力留在 `device_api`
- 缩减 `automation` 在采集主链中的角色
- 为最终完全切流做准备

### P3：文档与测试维护

- 功能变化后同步更新根目录 `doc/`
- 补齐关键测试样例
- 定期清理过期说明，避免文档再次膨胀

## 5. 推荐跟进方式

每次进入 `device_api` 工作前，先确认三件事：

1. 当前改动是否符合标准化结果合同
2. 当前改动是否会让能力回流到 `apps.automation`
3. 当前改动是否同步补了测试或说明
