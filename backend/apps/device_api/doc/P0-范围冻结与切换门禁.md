# P0 范围冻结与切换门禁基线

## 1. 结论

截至 2026-03-16，`device_api` 的 P0 基线已经冻结：

- 默认主链目标固定为 `plan_collect_device_main -> plan_collect_device`
- `automation` 保留为 fallback，不进入新增能力开发
- 首批切换仅覆盖当前主矩阵的 CLI/NETCONF 能力，不把 Telemetry 计入通过项
- 灰度对比、回退演练、生产追溯阶段禁止强制清空历史 `plan_*` 结果

本文件只回答 P0 的三个问题：

1. legacy 现状是什么
2. `device_api` 当前到底覆盖到哪里
3. 默认切换和回退的门禁是什么

## 2. 基线来源

代码基线来源：

- `backend/apps/automation/tasks.py`
- `backend/apps/automation/models.py`
- `backend/apps/device_api/tasks.py`
- `backend/apps/device_api/platform_profiles.py`
- `backend/apps/device_api/processors/`
- `backend/apps/device_api/connection_manager.py`

当前库样本基线来源：

- `CollectionPlan.objects.count() == 14`
- `PlansToDevice.objects.count() == 59`
- `PlansToDevice` 当前绑定分布：`plan_id=None` 37 条，`plan_id=3` 22 条

说明：

- 本地数据库存在 `device_api` 新字段未完全迁移的问题，不能把 ORM 全量查询结果当作生产事实
- 因此 P0 文档同时保留“代码支持矩阵”和“当前库里可见样本矩阵”两套口径
- “生产实际在用”必须在后续灰度前再用线上/准生产数据复核一次，P0 先冻结代码与当前样本的最小边界

## 3. legacy 盘点

### 3.1 当前库里可见的 `automation.CollectionPlan`

| vendor | category | plans | 主要命令/方法特征 |
|---|---|---:|---|
| H3C | 交换机 | 5 | CLI + NETCONF 双栈最完整，覆盖 ARP/MAC/LLDP/接口/聚合/BGP 等 |
| Huawei | 交换机 | 4 | S/CE/防火墙相关方案，CLI + NETCONF 双栈 |
| Ruijie | 交换机 | 1 | 以 CLI 为主，覆盖接口/ARP/MAC/聚合 |
| Hillstone | 交换机 | 1 | 以 CLI 为主，兼带安全域/策略类命令 |
| Maipu | 交换机 | 1 | CLI 为主 |
| Mellanox | 交换机 | 1 | CLI 为主 |
| Centec | 交换机 | 1 | CLI 为主 |

当前库样本中未看到独立的 Cisco / ZTE legacy 方案记录，但 `device_api` 代码已经预留这两类厂商入口，不能据此认定其生产不使用。

### 3.2 legacy 采集类型与执行方式

按代码和样本交叉确认，legacy 主链当前实际依赖的能力分为两层：

- 主矩阵基础类型：`device_identity`、`arp`、`mac`、`lldp`、`interface_brief`、`ip_interface`、`aggre_port`
- 扩展类型：`route_table`、`bgp_neighbors`、`bgp_summary`、`fan_status`、`power_status`、`session`

legacy 协议现状：

- Netmiko/CLI 是通用主路径
- H3C/Huawei 已形成真实 NETCONF 方法集合
- SNMP、RESTCONF、Telemetry 不是当前 legacy 主链替代的验收基线

### 3.3 legacy 结果表与清理语义

legacy `clear_his_collect_res()` 只清理：

- `collect_textfsm_info`
- `netconf_failed`
- `NETCONF` 库下的临时表

legacy 不会在每批前删除 `ARPTable`、`MACTable`、`LLDPTable` 等主结果表。

## 6. 首批切换范围与延期范围

### 6.1 首批切换范围

首批允许切换为 `device_api` 默认主链的范围：

- Huawei 交换机主矩阵
- H3C 交换机主矩阵
- 已有明确绑定且只使用 `netmiko` 子集的 Ruijie 设备
- 已有明确绑定且只使用 `arp/session` 子集的 Hillstone 设备

首批必须满足的额外门禁：

- 设备已经进入 `PlansToDevice`
- 父方案和子方案不是“表面启用、实际缺模板/缺方法”
- 批次运行时显式确认是否保留历史结果

### 6.2 延期范围

以下范围不阻塞首批切主链，但不得被误报为已完成：

- Cisco
- ZTE
- Maipu
- Mellanox
- Centec
- SNMP/RESTCONF 真实生产替代
- Telemetry 全部能力

## 7. fallback 与回退门禁

### 7.1 允许触发 `automation` fallback 的条件

只允许在运行策略层切换到 `automation`，不修改 `automation` 代码逻辑。

触发条件：

- 目标设备未进入 `PlansToDevice`
- 目标方案缺少可执行子方案、模板、XML、OID 或账号
- 主矩阵协议连续失败并达到灰度阈值
- `collection-results/latest/` 或事实接口无法稳定返回本批次结果
- 分析链路因 `device_api` 批次语义异常而无法继续消费

### 7.2 人工回退条件

出现以下任一情况，停止继续扩大 `device_api` 灰度：

- 批次成功率低于 legacy 基线
- 空结果率、模板缺失率或账号缺失率异常抬升
- 下游分析批次不能按 `execute_time` 正确关联
- 同批对比无法完成，因为历史数据被错误清理

### 7.3 停止条件

出现以下情况应直接停止本轮切换并回退：

- 关键厂商主矩阵出现系统性失败
- 同一批次结果被覆盖，无法进行灰度对照
- 需要通过改 `automation` 代码才能恢复生产

## 8. `clear_his_collect_res()` 复核结论

`device_api.clear_his_collect_res()` 当前会删除：

- `COLLECTION_SUB_PLAN`
- 全部 `plan_<collection_type>` 标准结果集合

这比 legacy 清理策略更激进，会直接影响：

- 生产追溯
- `automation` 与 `device_api` 并行对比
- 回退演练的证据保留

P0 结论：

- 默认行为暂不改为“永不清理”，以避免影响既有批次运行习惯
- 但从本次起，主调度必须支持显式 `clear_history=False`
- 灰度对比、回退演练、人工排障批次一律使用 `clear_history=False`
- 只有“确认无需保留历史对照”的日常覆盖式批次才允许清理
