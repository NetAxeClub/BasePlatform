# 采集方案：旧版（automation）与新版（device_api）对比与选型建议

## 一、两套方案概览

| 维度 | 旧方案（automation） | 新方案（device_api） |
|------|----------------------|----------------------|
| **入口** | `automation/tasks.py`：`collect_device_main` → `collect_device` | `device_api/tasks.py`：`plan_collect_device_main` → `plan_collect_device` |
| **设备与方案** | 设备带 `plan_id`，指向 `CollectionPlan`（单表） | 设备带 `plan_id`，指向 `DeviceCollectionPlans`（父方案），其下多条 `DeviceSubCollectionPlan`（子方案） |
| **厂商适配** | `automation/tools/`：H3cProc、HuaweiProc 等，继承 BaseConnection，重写 `collection_run` / `_collection_analysis` | `device_api/tools/`：按厂商类 + 采集类型方法（如 `get_arp`、`get_mac`）；`device_api/processors/` 注册预处理函数；`connection_manager` 统一连接 |
| **配置模型** | 一个方案 = 一套 `commands`（JSON）+ `netconf_method`（JSON）+ `netconf_class`，无「采集类型」「字段映射」表结构 | 父方案 + 多子方案；子方案有 `collection_type`、netmiko/netconf 开关、path、`field_mappings` 等 |
| **数据与存储** | 解析逻辑写在各厂商 Proc 内，结果写固定 Mongo 表（ARPTable、MACTable、layer2interface 等） | 按 `collection_type` 路由到 `plan_arp`、`plan_mac` 等集合；支持字段映射 + 后端处理器 |

## 二、旧方案（automation）特点

### 2.1 结构

- **CollectionPlan**：单表，字段包括 vendor、category、name、commands（JSON 命令列表）、netconf_method（JSON）、netconf_class。设备关联一个 plan_id。
- **调度**：`collect_device_main()` 调用 `get_device_info_v2()` 拉取设备列表（status=0、auto_enable=True、有 plan_id 等），对每台设备下发 `collect_device.apply_async(host)`。
- **单设备执行**：根据 `host['vendor__alias']` 选 CLASS_MAP 中的 Proc（如 H3cProc），传入整机 host 信息，执行 `class_instance.collection_run()`。
- **collection_run**（base_connection）：从 `self.plan['commands']` 取命令列表，`_send_cmd(cmds)` 用 Netmiko 执行并落盘，再 `_collection_analysis(paths)` 解析；netconf 逻辑在各子类中自行扩展。
- **解析与落库**：由各厂商 Proc 的 `_collection_analysis`、netconf 相关方法完成，直接写 Mongo（ARPTable、MACTable、layer2interface 等），无「字段映射」配置，无「采集类型」抽象。

### 2.2 优点

- 模型简单：一个方案一条记录，配置即「命令列表 + netconf 方法列表」。
- 当前线上在用，行为已被验证，与现有设备、资产、任务结果等已打通。

### 2.3 缺点与改造成本

- **tasks.py 体量极大**（约 4500 行）：除采集主流程外，还包含大量其它逻辑（如 standard_analysis_main、interface_used、tracking、消息发送等），采集与其它能力耦合在一起，改造「仅采集」需要谨慎抽离。
- **厂商逻辑集中在少数大文件**：如 h3c.py 约 1800 行、huawei.py 约 1600 行、hillstone 约 1500 行；新增/调整采集类型或厂商都要改这些巨型类，可维护性差。
- **无「采集类型」与「字段映射」模型**：若要支持「按类型配置、按类型落库、可配置字段映射」，需要在 automation 里引入子方案或等价结构，并重写执行与落库链路，工作量接近重做一套。
- **连接与执行方式**：每个 Proc 内自己建 Netmiko/NETCONF 连接，无统一「单设备多子任务复用同一连接」的抽象，若要优化为「一设备一次连接、多命令/多类型」需要改所有 Proc。
- **数据预处理**：全部写在厂商代码里，无法做到「配置化 + 后端注册处理器」的形态；若要做成「硬编码在后端函数、按类型调用」，同样需要大规模重构。

**结论**：在「持续改进、减少用户操作、支持字段映射与类型化」的目标下，在旧方案上改造的代价高、风险大，且难以在不重写核心执行路径的前提下达到与新方案类似的可扩展性。

## 三、新方案（device_api）特点

### 3.1 结构

- **DeviceCollectionPlans + DeviceSubCollectionPlan**：父方案下多条子方案，子方案带 `collection_type`、netmiko/netconf 启用、path、field_mappings 等；设备关联父方案 plan_id。
- **调度**：`plan_collect_device_main()` 调用 `get_auto_device()` 拉取设备并预加载每台设备对应的 sub_plans，对每台设备下发 `plan_collect_device.apply_async(host)`，host 中带 `sub_plans`。
- **单设备执行**：`DeviceConnectionManager` 单设备建一次连接，按 netmiko/netconf 分组执行各 sub_plan（命令/模板从 sub_plan 取），结果交 `_process_and_save_result` → `resolve_raw_data`（字段映射 + 可选处理器）→ 按 collection_type 落 Mongo。
- **厂商与类型**：`device_api/tools/` 下按厂商类 + 方法名（如 `get_arp`、`get_mac`）组织；`fields_mapping.py` 定义采集类型与默认映射；`processors/` 可注册预处理函数；连接、执行、落库分层清晰。

### 3.2 优点

- **采集类型与存储解耦**：collection_type 决定 Mongo 集合与处理链路，新增类型主要增配置和少量方法，不必改巨型单文件。
- **字段映射可配置**：path + field_mappings 存库，支持「仅字段映射」或「后端处理器 + 字段映射」，满足当前产品方向（数据处理硬编码在后端）。
- **连接复用**：单设备一次连接执行多子方案，逻辑集中在 `DeviceConnectionManager` 和 `plan_collect_device`，易于维护和扩展。
- **任务与模型体量可控**：device_api/tasks.py 约 680 行，tools 下各厂商文件百行级，总体约 2.8k 行，比 automation 的 11k+ 行轻很多。
- **已有简化方案文档**：可在现有模型上做「父方案级启用类型 + 采集方式、自动同步子方案、聚合字段映射、一键验证」等 UX 优化，而无需推倒重来。

### 3.3 缺点与需要补齐的

- 当前产品若仍主要在使用 automation 的入口与设备列表，需要把「主入口」与「设备关联方案」逐步切到 device_api（或做双写/分流），并统一由 `plan_collect_device_main` 调度。
- 新方案依赖设备有 `plan_id` 指向 DeviceCollectionPlans，且需保证 get_auto_device 与资产、账号等数据源一致。
- 若部分厂商/类型在 automation 有实现而 device_api 尚未覆盖，需要按 device_api 的 tools/processors 规范补全，而不是回到 automation 的 Proc 里加。

## 四、对比小结（表）

| 评估项 | 旧方案（automation） | 新方案（device_api） |
|--------|----------------------|----------------------|
| 模型与扩展性 | 单表、无类型/映射抽象；扩展需改大段厂商代码 | 父+子、类型+字段映射；扩展以配置和小方法为主 |
| 代码体量与可维护性 | tasks 约 4500 行，单厂商文件上千行，耦合多 | tasks 约 680 行，厂商文件百行级，职责清晰 |
| 连接与执行 | 每厂商自己建连接，无统一复用 | 单设备连接复用，统一 ConnectionManager |
| 字段映射与预处理 | 无配置化映射；预处理全在厂商代码里 | 有 path + field_mappings；可接后端硬编码处理器 |
| 简化 UX 的可行性 | 需引入子方案/类型/映射概念并重写执行链 | 已有子方案与类型，仅需父方案级配置 + 自动同步 + 聚合接口 |
| 改造与迁移成本 | 在现有结构上做「类型化+映射+简化操作」成本高 | 在现有结构上做「简化操作」成本低，已有改进方案文档 |

## 五、选型建议

**建议：以「新方案（device_api）」作为长期主采集方案，在其上持续改进优化；旧方案（automation）可作为过渡或只读兼容，不推荐再投入大量改造。**

理由简述：

1. **目标匹配**：你要的是「减少用户操作、最小代价完成方案制定与验证、数据处理硬编码在后端」——这些在新方案里都能通过「父方案级配置 + 自动同步子方案 + 字段映射聚合 + 一键验证」实现，且已有《采集方案简化与优化方案》可落地；旧方案要达成类似效果需要引入子方案、类型、映射并重写执行与落库，代价大。
2. **可维护性与扩展性**：新方案代码更集中、更小，类型与厂商扩展以配置和小方法为主；旧方案单文件过大、耦合多，后续加类型、加厂商、改逻辑都更难。
3. **技术债务**：旧方案 tasks 与 tools 体量大、职责混杂，若在其上继续做「简化操作」和「字段映射」，很容易再堆高债务；新方案债务相对小，更适合作为主战场。
4. **迁移策略**：若当前线上仍以 automation 为主，可采取「新设备/新方案统一走 device_api，旧任务保留 automation 入口」的分流策略，逐步把调度主入口和前端配置切到 device_api，待稳定后再考虑下线 automation 的采集入口。

---

## 六、若选择「继续用旧方案」需要注意的点

若因短期原因必须继续使用 automation 作为主入口，建议至少：

- 将「采集主流程」与 tasks.py 中其它逻辑（分析、追踪、通知等）解耦，便于单独替换为 device_api 的调度与执行。
- 不再在 automation 的 Proc 里大规模新增「类型化、字段映射、可配置预处理」等能力，避免进一步放大单文件与耦合；新能力优先在 device_api 实现，通过统一入口或分流逐步切换。

这样可以在过渡期保持稳定，同时为最终切到新方案留出清晰路径。
