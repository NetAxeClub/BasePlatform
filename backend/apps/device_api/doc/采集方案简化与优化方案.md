# 采集方案简化与优化方案

> 备注（2026-03-03）：运行时数据入库链路已不再依赖子方案字段映射执行，字段映射更适合作为“标准字段说明/兼容配置”而非必填步骤。

## 一、现状与问题

### 1.1 当前用户操作路径（过长）

1. **建父方案**：填写名称、厂商、设备类型、描述等。
2. **建子方案**：为父方案下逐个新建子方案（或依赖「创建空白方案时自动生成所有类型子方案」）。
3. **配置子方案**：每个子方案需单独：
  - 选择/确认「采集类型」（arp、mac、lldp、interface_brief 等）；
  - 勾选「启用 Netmiko」/「启用 NETCONF」及对应方法、路径；
  - 配置「字段映射」。
4. **数据处理**：已改为后端硬编码/预定义处理器，用户侧无配置。
5. **验证**：再选设备做执行验证。

结果：**点击和页面层级多、概念多（父/子、采集类型、采集方式、字段映射），使用成本高。**

### 1.2 核心诉求

- **最少点击、最少步骤**完成「一个采集方案的制定与验证」。
- **子方案**对用户弱化或不可见，不再让用户「先建方案再建子方案、再按类型/方式逐个配置」。
- **采集类型**不在子方案上由用户选择，而是由后端按「方案 + 类型」固定派生。
- **数据预处理**完全后端硬编码（按厂商+设备类型+采集类型调用既定函数），用户无配置。

---

## 二、优化目标


| 目标       | 说明                                                                  |
| -------- | ------------------------------------------------------------------- |
| 减少步骤     | 从「父方案 → 多子方案 → 每子方案多配置项」收敛为「一次方案配置 + 少量必填项」。                        |
| 弱化子方案    | 子方案作为后端实现细节，由系统按「采集类型」自动生成与维护；用户不创建/不删除子方案。                         |
| 隐藏采集类型选择 | 采集类型由后端枚举（如 field_mapping 的 key），每个类型对应一条系统子方案；用户只需「勾选要采集的类型」或默认全开。 |
| 统一采集方式   | 方案级统一「采集方式」（如仅 Netmiko、仅 NETCONF、或两者），避免每个子方案单独勾选。                  |
| 字段映射收敛   | 在一个界面按「采集类型」分 Tab/表格配置 path + 字段映射，或使用后端默认映射，用户仅改必要项。               |
| 一键验证     | 方案级「验证」：选一台设备，一次执行当前方案下所有启用的采集类型并展示结果。                              |

## 三、产品形态建议（最小代价）

### 3.1 用户侧只保留「采集方案」一层

- **新建/编辑采集方案**只看到一个表单，包含：
  - **必填**：方案名称、厂商、设备类型。
  - **可选**：描述、是否启用。
  - **采集类型**：多选（ARP、MAC、LLDP、二层接口、三层接口、聚合端口等），**默认全选**；未选中的类型不采集、不展示。
  - **采集方式**：单选项——「仅 Netmiko」「仅 NETCONF」「Netmiko + NETCONF」；所有选中类型共用该方式。
  - **字段映射**（可选收起）：按采集类型 Tab 或表格展示，每类仅「根节点 path + 字段映射」；可预填后端默认，用户只改需要改的。
- **不再有**：「新建子方案」「编辑子方案」「为每个子方案选采集类型/勾选 Netmiko/NETCONF」等单独操作。

### 3.2 后端模型与数据（兼容现有表结构）

- **父方案** `DeviceCollectionPlans`：保留；可增加字段（或复用现有）：
  - `enabled_collection_types`：JSON 数组，如 `["arp","mac","lldp",...]`，表示要采集的类型；空或未传则视为全部启用。
  - `collection_method`：枚举，如 `netmiko` / `netconf` / `both`，表示方案级采集方式。
- **子方案** `DeviceSubCollectionPlan`：
  - **不再由用户创建/删除**；在「保存父方案」时由后端根据 `enabled_collection_types` 自动同步（有则更新、无则创建、取消勾选则软删或禁用）。
  - **采集类型**：由后端根据该子方案在列表中的位置或唯一键（如 `summary_plan_id + collection_type`）确定，**子方案表仍保留 `collection_type` 字段**，但仅后端写入，前端不展示「采集类型」下拉框。
  - **Netmiko/NETCONF**：由父方案 `collection_method` 写入各子方案的 `netmiko_enabled` / `netconf_enabled`，用户不再逐条勾选。
  - 子方案名称可继续自动生成，如 `{父方案名}-{collection_type}`。

这样**不强制拆表**，仅约束「子方案由后端按类型自动维护」，前端只操作父方案。

### 3.3 数据处理（硬编码在后端）

- 数据预处理**不向用户开放**任何配置。
- 执行时按「厂商 + 设备类型 + 采集类型 + 采集方式」调用既有或新增的**后端硬编码函数**（如 `processors`、`tools` 下按类型映射）；字段映射仍用现有 `netmiko_field_mappings` / `netconf_field_mappings` 等。
- 若某类型暂无后端处理函数，可回退为「仅做字段映射」或标记该类型暂不可用。

### 3.4 接口与前端简化


| 操作   | 当前                                 | 优化后                                                           |
| ---- | ---------------------------------- | ------------------------------------------------------------- |
| 新建方案 | 建父方案 → (可选)建多个子方案 → 每子方案配置类型/方式/映射 | **一次「新建采集方案」**：填名称、厂商、设备类型、勾选采集类型、选采集方式、可选配字段映射；后端自动生成/更新子方案。 |
| 编辑方案 | 编辑父方案 + 逐个编辑子方案                    | **一次「编辑采集方案」**：改父方案字段 + 勾选类型 + 采集方式 + 字段映射；后端同步子方案。           |
| 详情   | 父方案详情 + 子方案列表 + 进子方案再看类型/方式/映射     | **一个详情页**：父方案信息 + 采集类型勾选情况 + 采集方式 + 按类型展示的字段映射（只读或内嵌编辑）。      |
| 验证   | 选设备、选子方案或类型再执行                     | **方案级验证**：选一台设备，一键执行当前方案下所有启用类型，结果按类型分块展示。                    |

## 四、后端改动要点（按阶段）

### 4.1 第一阶段：父方案带「启用类型 + 采集方式」（最小改动）

- 父方案表增加（或复用）：
  - `enabled_collection_types`（JSONField，可选）：如 `["arp","mac","lldp","interface_brief","ip_interface","aggre_port"]`，空表示全部启用。
  - `collection_method`（CharField，可选）：`netmiko` / `netconf` / `both`。
- **创建/更新父方案接口**：
  - 接收上述两字段；
  - 在 `create`/`update` 时根据 `enabled_collection_types` 与 `DEFAULT_COLLECTION_TYPES` 对比，**自动同步子方案**（创建缺失的、禁用未选的、更新 `netmiko_enabled`/`netconf_enabled` 为方案级 `collection_method` 的派生）。
- **子方案接口**：
  - 列表/详情仍可保留给前端「按类型展示」只读；**不再提供「新建子方案」入口**（或保留仅后端用）。
  - 子方案 `collection_type` 仅后端写入，前端不提供「采集类型」选择。

### 4.2 第二阶段：字段映射聚合展示与回写

- **按方案维度的字段映射接口**（推荐）：
  - GET：返回 `{ "arp": { "netmiko_path", "netmiko_field_mappings", "netconf_path", "netconf_field_mappings" }, "mac": { ... }, ... }`，由后端从各子方案按 `collection_type` 聚合。
  - PUT/PATCH：接收同结构，后端按类型回写到对应子方案。
- 前端一个页面按类型 Tab/表编辑 path 与映射，减少来回切子方案。

### 4.3 第三阶段：一键验证与结果展示

- **方案级验证接口**：入参 `plan_id`、`device_ip`（或设备 ID）；后端解析该方案下所有启用子方案，一次执行（沿用现有执行链路），返回按 `collection_type` 分组的执行结果与简要状态。
- 前端：方案详情页「验证」按钮 → 弹框选设备 → 请求该接口 → 展示各类型采集结果。

### 4.4 数据预处理（已定）

- 保持「数据处理」不在用户侧配置；执行链中继续按「厂商 + 设备类型 + 采集类型 + 采集方式」走后端硬编码函数 + 字段映射，无需新增用户配置项。

## 五、子方案与「采集类型」的收敛方式（推荐）

- **子方案中保留 `collection_type` 字段**，用于后端存储与执行时路由（MongoDB 集合、处理器方法名等）。
- **从用户视角删除「采集类型」选择**的含义是：
  - 用户不选择「这个子方案是 arp 还是 mac」；
  - 用户只在父方案上勾选「要采集哪些类型」，后端为每个勾选类型保证恰好一条子方案（且 `collection_type` 由系统设定）。
- 这样**不删表、不删字段**，只删「子方案 + 采集类型」的用户操作，实现「最小代价、最大减负」。

## 六、验收要点（简化后）


| 项    | 说明                                                                |
| ---- | ----------------------------------------------------------------- |
| 新建方案 | 用户只填一份表单（名称、厂商、设备类型、可选启用类型、采集方式、可选字段映射），即可完成方案创建；子方案由后端自动生成且类型正确。 |
| 编辑方案 | 同一表单编辑；修改启用类型或采集方式后，子方案自动同步，无需进入子方案列表逐条改。                         |
| 详情   | 一个详情页看到方案信息 + 启用类型 + 采集方式 + 按类型聚合的字段映射，无需点进多条子方案。                 |
| 验证   | 方案详情页选设备一键验证，一次请求返回所有启用类型的执行结果。                                   |
| 执行   | 现有按设备+方案执行的任务逻辑不变，仍按子方案列表执行；子方案列表由后端根据父方案自动维护。                    |


---

## 七、小结

- **用户侧**：只操作「采集方案」一层；采集类型以「多选勾选」出现，采集方式以方案级单选出现；字段映射按类型聚合到一个页面；验证为一键选设备出结果。
- **后端**：父方案增加（或复用）`enabled_collection_types`、`collection_method`；在保存父方案时自动同步子方案（含 `collection_type`、netmiko/netconf 启用状态）；子方案不再对用户开放「新建/选类型/选方式」；数据处理保持后端硬编码。
- **子方案与采集类型**：子方案表保留 `collection_type` 等字段，仅后端维护；对用户「删除」的是子方案与采集类型的**操作与展示**，不是表结构，从而以最小代价完成采集方案的制定与验证。
