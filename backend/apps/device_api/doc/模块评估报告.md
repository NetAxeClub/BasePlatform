# device_api 模块评估报告

更新时间：2026-03-03

## 1. 模块定位

`device_api` 已承担“统一管理网络设备采集 + 标准化入库”的主链路能力，覆盖：

- 协议执行：Netmiko / NETCONF / SNMP / RESTCONF / Telemetry（Telemetry 当前为占位）
- 方案模型：父方案 `DeviceCollectionPlans` + 子方案 `DeviceSubCollectionPlan`
- 数据处理：`processors/`（结构解析）+ `tools/`（兜底规范化）+ 元数据注入
- 入库：按 `collection_type` 写入 `Automation.plan_{type}` 集合

## 2. 已实现情况（按核心链路）

### 2.1 采集执行链路

- 主调度：`tasks.py` `plan_collect_device_main` / `plan_collect_device`
- 单设备连接复用：`connection_manager.py` `DeviceConnectionManager`
- 子方案执行后处理：`tasks.py` `_process_and_save_result`

结论：主链路可用，结构清晰。

### 2.2 数据预处理链路（当前）

- 入口：`models_api.py` `resolve_raw_data`
- 优先级：
  1. `processors` 注册处理器
  2. `tools` 厂商方法兜底（主要 Netmiko）
  3. `inject_metadata` 注入 `hostip/hostname/idc_name/log_time`

关键变更：运行时已不再执行 `apply_field_mappings` 做入库前字段映射。

### 2.3 标准字段约束

- 来源：`fields_mapping.py` `field_mapping`
- 新增能力：处理器输出会按 `collection_type` 标准字段自动补齐缺省值（list 字段补 `[]`，其他补空字符串）

结论：字段一致性由“处理器 + 标准字段定义”保证，不再依赖子方案字段映射配置。

## 3. 当前缺口

1. 部分 NETCONF 处理器仍是 TODO（例如 H3C/Huawei 若干类型）
2. Cisco/Ruijie/Hillstone 处理器仍以透传为主，标准化深度不足
3. 父方案级的“启用类型 + 采集方式统一配置 + 一键验证”尚未完整落地
4. 自动化测试覆盖不足（缺处理器/预处理链路单测）

## 4. 风险与建议

1. 若某些 NETCONF 类型没有可用处理器，当前会明确失败，不会再依赖字段映射兜底
2. 建议优先补齐 H3C/Huawei NETCONF TODO 处理器，避免影响该协议覆盖面
3. 子方案层面建议将字段映射相关字段降级为“兼容保留，不参与运行”

## 5. 结论

模块已具备“处理器驱动的统一采集入库”骨架；本轮改造后，配置复杂度与运行时分支复杂度均下降。下一阶段应聚焦“处理器覆盖率”和“方案配置体验”两项闭环。
