# 统一验收流程与结论模板

## 1. 适用范围

本文件适用于 NetClaw-CN 改造在 NetAxe backend 侧的全部阶段验收。

所有 phase 必须使用本文件定义的统一输入项、输出项、决策规则和结论模板，不允许单独发明新的验收口径。

## 2. 验收输入项

每个阶段提交验收时，研发负责人必须提供完整“阶段完成包”，至少包含：

- 代码范围
- 已完成需求清单
- 接口变更清单
- 模型变更清单
- 测试报告
- 风险说明
- 回滚方案
- 遗留问题
- 证据文件引用

若缺任一关键输入项，验收负责人可直接判定为 `REJECT`。

## 3. 验收输出项

每个阶段验收结论必须统一记录以下字段：

- `phase`
- `decision`
- `summary`
- `blocking_issues`
- `waivers`
- `required_followups`
- `evidence_refs`
- `accepted_by`
- `accepted_at`

## 4. 决策规则

### 4.1 PASS

满足条件：

- 所有硬门槛通过
- 关键测试通过
- 架构边界符合总控文档
- 审计与追溯闭环成立
- 没有阻塞上线问题

### 4.2 PASS_WITH_WAIVER

满足条件：

- 核心目标达成
- 存在少量已登记、已限界、可接受风险
- 风险不阻塞阶段推进
- 已登记豁免、截止时间和复核条件

### 4.3 REJECT

任一情况成立即可拒绝：

- 存在阻塞问题
- 关键证据缺失
- 关键测试未通过
- 审计、回滚或执行闭环不成立
- 新能力回流 legacy 主链

## 5. 验收流程

### 步骤 1：提交阶段完成包

研发负责人提交：

- 阶段目标完成说明
- 代码与接口清单
- 测试与证据
- 风险与遗留问题

### 步骤 2：执行 gate 审查

验收负责人按固定维度审查：

- 需求完成度
- 架构一致性
- 接口合同稳定性
- 测试与回归覆盖
- 审计与回滚闭环
- legacy 依赖是否扩散
- 风险是否已登记并限界

### 步骤 3：形成正式结论

输出以下之一：

- `PASS`
- `PASS_WITH_WAIVER`
- `REJECT`

### 步骤 4：写回文档

必须回写：

- 对应 phase 文档末尾“验收结论”
- `07-风险台账与豁免记录.md`
- `README.md` 阶段状态总览

### 步骤 5：决定是否进入下一阶段

- `PASS`：可进入下一阶段
- `PASS_WITH_WAIVER`：可进入下一阶段，但必须附带豁免跟踪
- `REJECT`：不得进入下一阶段，必须先整改再复验

## 6. 阶段必查清单

所有阶段验收必须至少检查与本阶段相关的以下通用项：

- 设备画像与自动绑定
- 单设备巡检
- 批量巡检与 partial 结果
- 安全审计结果回放
- 变更审批、baseline、verify、rollback
- agent 接口稳定性
- legacy 依赖不回流
- 权限与审计链完整

## 7. 验收结论模板

建议使用以下 Markdown 模板：

```md
## 验收结论

- Phase：Phase X
- Decision：PASS / PASS_WITH_WAIVER / REJECT
- Summary：一句话总结阶段结论
- Blocking Issues：
  - ...
- Waivers：
  - ...
- Required Follow-ups：
  - ...
- Evidence Refs：
  - ...
- Accepted By：验收负责人
- Accepted At：YYYY-MM-DD HH:MM:SS
```

## 8. REJECT 时的整改模板

若阶段未通过，必须追加以下内容：

```md
## 整改项清单

- RID-001：问题描述，整改负责人，截止时间
- RID-002：问题描述，整改负责人，截止时间

## 复验触发条件

- 条件 1
- 条件 2
```

## 9. PASS_WITH_WAIVER 时的豁免模板

```md
## 豁免项

- WVR-001：问题描述，影响范围，截止时间，复核条件
- WVR-002：问题描述，影响范围，截止时间，复核条件
```

## 10. 验收负责人的职责

- 验收负责人是每阶段唯一 gate reviewer
- 验收负责人不代替研发实现，但对是否满足放行条件给出正式判断
- 验收负责人有权要求补测试、补证据、补接口说明、补回滚方案
- 阶段未通过时，必须给出明确阻塞项，不允许笼统结论
