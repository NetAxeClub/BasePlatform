# NetClaw-CN 总控说明与治理机制

## 1. 项目目标

NetClaw-CN 改造目标是把 NetAxe backend 从“设备能力与局部运维模块集合”升级为“面向 agent 的统一网络运维后端控制面”。

最终目标包括：

- 对外统一暴露设备事实、设备能力、巡检、安全审计、变更执行、执行状态、回滚与审计留痕
- 对内统一收敛 `device_api`、`asset`、`config_center`、`api`、`topology`、`workflow_center`、`network_analysis`、`dcs_control`
- 对遗留模块建立冻结边界，防止新功能回流 `automation`
- 为后续 MCP / Skill 产品化提供稳定 REST 合同

## 2. 成功标准

本次改造最终视为成功，必须同时满足以下条件：

- NetAxe 能作为 NetClaw-CN 的统一后端，而不是多个内部模块的拼接代理
- 主链能力覆盖 facts、inspection、security audit、change、analysis、execution query
- 高风险操作具备审批、基线、验证、回滚和审计闭环
- `automation` 不再承接任何新功能开发
- OpenClaw / MCP / Skill 不需要直接消费零散内部 app 接口

## 3. 改造原则

- 新主链优先：新增能力优先进入新主链，不回流 legacy
- 遗留冻结：`automation` 仅保留兼容、回退和迁移价值
- 平台统一：NetAxe 是统一后端，不采用 prompt 拼接多接口模式
- 原生优先：国产设备优先使用 NetAxe 原生南向能力
- 合同优先：先统一 API / 数据合同，再扩功能
- 审计优先：没有执行留痕、验证结果和风险说明的功能，不视为可上线
- 产品化优先：`device_api`、`asset`、`config_center`、`api`、`topology`、`dcs_control` 的 phase 设计必须以 NetAxe 自身产品化为目标，并联动前端页面重构，而不是只从 NetClaw-CN 对接角度出发
- 非依据模块排除：`automation`、`monitor`、`support` 不作为设计、实施、验收依据

## 4. 领域边界

### 4.1 southbound_core

职责：

- 厂商画像与设备能力匹配
- 采集方案、模板、协议矩阵
- 本地执行与南向执行统一结果合同
- 标准化结果入库与回调

当前主要来源：

- `apps/device_api`

### 4.2 ops_execution_center

职责：

- 统一任务执行台账
- 审批、执行、验证、回滚状态机
- 工单、执行者、触发源、证据、风险绑定
- 为 agent 提供统一 execution query

当前主要来源：

- `apps/workflow_center`

### 4.3 network_intelligence_center

职责：

- 接口利用率、地址定位
- 事实拓扑、路由健康、设备健康
- 配置漂移、事实漂移、批次分析

当前主要来源：

- `apps/network_analysis`
- `apps/topology` 的可复用事实能力，但不复用手工图主链

### 4.4 security_policy_center

职责：

- 安全策略统一审计
- 高危暴露检测
- 变更前后安全差异分析
- 安全审计留痕

当前主要来源：

- `apps/dcs_control`

## 5. 模块处理原则

| 模块 | 定位 | 处理原则 |
|---|---|---|
| `device_api` | 主链 | 继续增强，承担 southbound_core 核心职责，并作为 NetAxe 网络设备原子能力中心 |
| `asset` | 主链基础事实 | 继续增强，承接设备事实与能力快照，但模型变更需经你同意 |
| `config_center` | 主链支撑 | 纳入后续 phase 设计视角，但必须以 NetAxe 产品化和前端重构协同为前提 |
| `api` | 主链支撑 | 纳入统一接口与前端协同设计视角 |
| `workflow_center` | 主链 | 演进为 ops_execution_center |
| `network_analysis` | 主链 | 演进为 network_intelligence_center |
| `topology` | 主链支撑 | 纳入 phase 设计视角，但以 NetAxe 产品化与前端重构为目标，不以旧手工图主链为依据 |
| `dcs_control` | 主链 | 抽取 security_policy_center 能力，并纳入前端联动规划 |
| `automation` | 遗留 | 冻结，不承接新需求 |
| `monitor` | 遗留 | 冻结，不承接新需求 |
| `support` | 遗留 | 冻结，不承接新需求 |

## 6. 角色定义

### 6.1 研发负责人

职责：

- 组织阶段实施
- 控制开发范围与优先级
- 提交阶段完成包
- 协调补测试、补证据、补边界说明

### 6.2 模块负责人

职责：

- 对所属模块的需求拆解和代码质量负责
- 保证模块改造符合总控文档
- 提交模块级风险、依赖和遗留问题

### 6.3 验收负责人

职责：

- 作为每阶段唯一 gate reviewer
- 对阶段是否满足放行条件给出正式结论
- 审查需求完成度、架构一致性、接口稳定性、测试覆盖、审计闭环和风险限界
- 有权要求补测试、补证据、补接口说明、补回滚策略

本项目中，验收负责人即本轮 NetClaw-CN 总体验收 owner。后续每阶段验收均以其书面结论为准。

## 7. Gate 机制

每阶段只允许以下三种结论：

- `PASS`
  - 所有硬门槛通过
  - 没有阻塞上线的问题
- `PASS_WITH_WAIVER`
  - 存在已登记、已限界、可接受的残余风险
  - 必须登记豁免条目、截止时间和复核条件
- `REJECT`
  - 存在阻塞问题，或关键证据缺失，或闭环不成立

## 8. 阶段推进规则

- 未完成当前阶段正式验收，不得进入下一阶段实施
- 若验收结论为 `REJECT`，必须形成整改项清单
- 若验收结论为 `PASS_WITH_WAIVER`，必须登记豁免并安排复验
- 任一阶段新增范围、调整目标或放宽标准，必须先更新文档再实施

## 9. 文档更新规则

- `README.md` 负责总览状态
- 每个 phase 文档负责该阶段的目标、任务、交付物、验收标准和结论
- `06-统一验收流程与结论模板.md` 负责统一验收口径
- `07-风险台账与豁免记录.md` 负责全局风险和豁免

每阶段结束时必须同步更新：

- 阶段状态
- 测试与证据引用
- 风险项状态
- 验收结论

## 10. 禁止事项

- 不允许在 `automation` 中继续落新主链能力
- 不允许以 `monitor`、`support` 作为本轮 phase 设计依据
- 不允许用临时脚本替代正式执行链和审计链
- 不允许在未形成统一合同前直接让 agent 拼接多个内部接口
- 不允许用“口头通过”“默认放行”代替书面验收结论
