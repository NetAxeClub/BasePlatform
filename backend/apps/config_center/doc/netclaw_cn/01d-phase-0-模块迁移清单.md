# Phase 0 附录 D：模块迁移清单

## 1. 文档目的

本文件定义各模块在后续 phase 中需要承接、保留、替代或冻结的能力，作为排期与验收的统一迁移清单。

## 2. 模块迁移总表

| 模块 | 当前状态 | 后续承接能力 | 被替代/冻结部分 | Phase 关注点 |
|---|---|---|---|---|
| `device_api` | 已形成默认采集主链 | facts、capabilities、设备画像匹配、父子采集方案、南向执行标准化 | 对 `automation` 的历史桥接能力最终应下沉为兼容层 | 保持新主链优先，不回流 legacy |
| `asset` | 设备与基础关系底座 | 设备事实、资产画像、能力快照绑定、设备唯一标识 | `NetworkDevice.plan -> automation` 只保留为 legacy 兼容关系 | 先冻结边界，再逐步拆旧依赖 |
| `workflow_center` | 执行编排基础待加强 | execution query、审批、执行、验证、回滚台账 | 零散执行状态分散在各 app 的历史方式 | 需在 Phase 2 成为统一执行中心 |
| `network_analysis` | 分析能力已存在 | 利用率、地址定位、批次分析、漂移分析 | 直接依赖旧拓扑手工图的思路 | 以事实分析为中心扩展 |
| `dcs_control` | 安全策略能力分散 | 安全策略审计、高危暴露检测、变更前后风险对比 | 与 legacy 执行链强耦合的历史实现 | 以统一审计输出为目标 |
| `config_center` | 配置支撑模块 | 配置模板、策略下发支撑、产品化页面联动 | 仅面向历史内部流程的零散实现 | 必须与前端联动一起设计 |
| `api` | 统一接口支撑待收敛 | agent API 出口、产品化页面支撑接口 | 各 app 直接裸露内部接口的做法 | 以统一入口替代多入口拼接 |
| `topology` | 旧拓扑能力仍在 | 事实拓扑、拓扑对账、拓扑分析支撑 | 手工图编辑主链地位 | 不以手工图作为未来主事实来源 |
| `automation` | 存量功能仍在线 | 仅作为兼容、回退、迁移链 | 所有新增主链需求 | 后续逐步去主链化 |
| `monitor` | 历史模块 | 无 | 整体不纳入本轮主链设计 | 非依据模块 |
| `support` | 历史模块 | 无 | 整体不纳入本轮主链设计 | 非依据模块 |

## 3. 重点迁移结论

### 3.1 `device_api`

- 后续 phase 的单设备 facts、capabilities、巡检入口都应优先围绕 `device_api` 组织。
- 现有父方案/子方案模型应被视为未来采集主链模型。
- 与 `automation` 的同步、桥接和 fallback 仅保留迁移期价值。

### 3.2 `asset`

- 继续作为设备主数据底座。
- 设备唯一标识优先采用 `serial_num` 等稳定标识。
- `NetworkDevice.plan` 明确定性为 legacy，不再作为新主链设计依据。

### 3.3 `workflow_center`

- Phase 1 允许先用过渡实现承接巡检与审计执行查询。
- 到 Phase 2 必须形成审批、执行、验证、回滚统一台账模型。

### 3.4 `topology`

- 旧 `topology` 现有页面与数据结构可保留运行。
- 未来事实拓扑、意图对比、漂移诊断不得继续围绕旧手工图主链设计。

### 3.5 `automation`

- 不再新增任何 NetClaw-CN 目标能力。
- 只允许承担 fallback、回退演练、对账、历史兼容职责。

## 4. 产品化与前端联动原则

以下模块的 phase 设计必须以 NetAxe 自身产品化和前端联动为目标：

- `device_api`
- `asset`
- `config_center`
- `api`
- `topology`
- `dcs_control`

约束说明：

1. 不能只从 NetClaw-CN 对接角度设计接口。
2. 需要考虑后台统一入口与未来前端页面的信息结构一致性。
3. 不允许因为兼容旧页面结构而牺牲新主链边界。

## 5. 与当前仓库现状的一致性说明

当前可确认的事实包括：

- `device_api` 已存在独立方案模型和 rollout 管理命令，具备承接主链的基础。
- `asset` 仍保留到 `automation.CollectionPlan` 的模型依赖，说明 legacy 切割尚未完成。
- `topology` 仍包含旧手工图读写逻辑，因此只能先冻结其未来主链地位。
- `monitor`、`support` 在仓库中仍存在，但不应再被纳入本轮架构依据。

## 6. 后续实施触发器

以下条件触发进入下一阶段的具体实现：

1. Phase 0 文档与验收结论齐备。
2. 统一 agent API 草案被冻结为实施依据。
3. 主链与遗留切割范围被所有后续 phase 继承，不再反复变更。
