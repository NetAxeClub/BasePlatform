# config_center 产品定位与边界方案

## 1. 文档目的

本文档用于明确 `apps.config_center` 的产品定位、功能边界、与 `apps.device_api` 的职责分工，以及后续收敛和重构计划。

适用前提：

- `device_api` 的产品定位已经明确为：负责异构多厂商的数据采集和配置下发，统一构建抽象层 API 能力。
- `config_center` 的产品定位必须围绕设备配置管理展开，不能与 `device_api` 的采集主链和下发主链形成长期重叠。

本文档的目标不是描述当前代码现状本身，而是给出 `config_center` 的目标产品口径，并据此识别当前实现中需要收敛的部分。

## 2. 当前结论

截至 2026-03-23，`config_center` 应明确定位为：

`设备配置管理与治理中心`

它负责围绕“设备配置”这一类对象提供全生命周期的管理能力，包括：

- 配置快照管理
- 配置版本追溯
- 配置合规与安全基线
- 配置结构化解析
- 配置漂移分析与治理
- 配置策略与审计留痕

它不负责建设异构设备南向协议采集底座，也不负责建设通用配置下发抽象层。这两部分是 `device_api` 的职责边界。

## 3. 产品定位

### 3.1 `device_api` 定位

`device_api` 是设备侧南向能力中心，负责：

- 面向多厂商、多协议的设备连接、采集、解析入口和执行编排
- 统一抽象采集与下发 API
- 统一处理厂商差异、协议差异、能力探测、执行失败语义
- 向其他 app 输出标准化的设备事实、采集结果和配置执行能力

一句话总结：

`device_api` 解决的是“如何和设备交互，并把能力抽象为统一 API”。

### 3.2 `config_center` 定位

`config_center` 是配置领域管理中心，负责：

- 围绕配置文本和配置结构化对象建立配置快照体系
- 提供配置版本、差异、回溯、基线、漂移、风险和审计能力
- 承接配置治理、配置分析、配置追责和配置运营视角的产品能力

一句话总结：

`config_center` 解决的是“配置采集之后如何管理、分析、治理和追溯”。

## 4. 功能边界

### 4.1 `config_center` 的职责范围

`config_center` 负责以下功能域：

1. 配置快照中心
   - 保存设备运行配置、启动配置等配置快照
   - 管理快照元数据、采集时间、设备信息、快照状态
   - 支持快照列表、详情、筛选、时间线和最新视图

2. 配置版本中心
   - 保存配置原文版本历史
   - 提供配置版本比较、历史回看、版本追溯能力
   - 对接 Git 或其他版本存储实现，但对产品层暴露的是配置版本语义，不是 Git 细节

3. 配置合规与基线中心
   - 管理配置规则树、厂商规则、安全基线
   - 执行配置合规检查
   - 关联某次配置快照保存合规结果
   - 提供规则解释、命中详情和历史追溯

4. 结构化配置中心
   - 将配置文本解析为统一结构化对象
   - 建立跨厂商统一 schema
   - 提供结构化快照查询和对象级视图

5. 配置漂移治理中心
   - 基于结构化快照做对象级 diff
   - 识别配置漂移、风险等级和关键变更
   - 支持白名单、豁免、抑制和风险说明

6. 配置策略与审计中心
   - 管理漂移策略、基线策略和策略版本
   - 支持预览、校验、激活、回滚
   - 对配置治理动作保留审计记录

### 4.2 `config_center` 的非职责范围

以下能力不属于 `config_center` 的产品边界：

- 新增任何通用南向协议接入能力
- 新增任何厂商连接适配器
- 建设通用设备采集编排主链
- 建设通用配置下发抽象层
- 管理设备协议登录、凭据协商、协议 fallback 策略
- 管理通用设备事实采集结果的标准合同
- 面向全平台承担“默认设备采集入口”

这些能力统一归属 `device_api`。

### 4.3 两个 app 的边界对照

| 领域 | `device_api` 负责 | `config_center` 负责 |
|---|---|---|
| 南向连接 | 多厂商多协议连接、执行、重试、超时、失败语义 | 不负责 |
| 通用数据采集 | ARP、MAC、LLDP、接口、路由、能力探测等采集主链 | 不负责 |
| 配置采集执行 | 设备配置采集的协议执行和厂商适配 | 不直接建设，优先复用 `device_api` 抽象能力 |
| 配置下发执行 | 通用配置下发 API、协议适配和执行编排 | 不负责执行底座，仅负责配置治理侧策略与审计 |
| 配置快照 | 不作为主产品对象管理 | 负责主产品对象管理 |
| 配置版本 | 不作为核心产品域 | 负责 |
| 配置合规 | 不负责配置治理产品能力 | 负责 |
| 配置结构化 | 可提供采集原始输入，不负责配置治理产品化视图 | 负责 |
| 配置漂移 | 不负责配置治理产品能力 | 负责 |
| 配置审计 | 不负责配置治理审计中心 | 负责 |

## 5. 协作原则

### 5.1 目标协作关系

两个 app 的目标协作关系应为：

- `device_api` 提供设备侧采集和下发抽象能力
- `config_center` 消费配置原文、配置执行结果或配置事件
- `config_center` 负责把配置对象转化为快照、版本、合规、结构化和漂移结果

推荐链路：

1. `device_api` 负责从设备拉取配置原文，或执行配置下发
2. `config_center` 负责保存配置快照
3. `config_center` 负责对快照执行版本留痕、合规校验、结构化解析和漂移分析
4. 若存在配置下发后的验证闭环，由 `config_center` 产出治理判断，执行仍由 `device_api` 负责

### 5.2 当前代码中的重叠点

当前实现中，`config_center` 仍然存在以下与目标边界不完全一致的地方：

- 存在直接连接设备执行配置备份的任务
- 存在偏底层的 Git 文件接口直接对外暴露
- 存在 regex、TTP、TextFSM、Jinja2 等研发调试工具接口与产品接口混放

这些能力在短期内可以保留以兼容现网，但不应继续扩展为长期产品边界。

## 6. `config_center` 的目标能力清单

### 6.1 对外产品能力

对业务、运营和治理侧，对外保留以下产品能力：

- 配置快照列表
- 配置快照详情
- 配置时间线
- 配置版本对比
- 配置合规结果查询
- 安全基线查询
- 结构化配置快照查询
- 结构化配置对比
- 结构化漂移查询
- 漂移策略管理
- 漂移审计记录

### 6.2 内部支撑能力

以下能力允许作为内部支撑能力存在，但不应作为 `config_center` 的一级产品定位对外宣传：

- TTP 模板管理
- TextFSM 模板调试
- regex 测试
- Jinja2 渲染调试
- 配置文件树浏览
- Git 原始提交浏览

这些能力后续应收敛到：

- 内部管理后台
- 研发运维工具域
- 仅管理员可见的配置治理后台

## 7. 模块设计建议

建议 `config_center` 后续按产品域收敛内部模块，而不是继续以单一大文件堆叠。

推荐拆分为以下领域：

1. `snapshot`
   - 配置快照对象
   - 快照查询
   - 快照时间线

2. `versioning`
   - 配置版本留痕
   - 历史版本内容
   - 配置 diff

3. `compliance`
   - 规则树
   - 厂商规则
   - 合规执行
   - 基线聚合

4. `structured`
   - 结构化解析
   - 标准 schema
   - 结构化快照存储

5. `drift`
   - 结构化 diff
   - 风险判断
   - 白名单与豁免

6. `governance`
   - 漂移策略
   - 策略版本
   - 激活、回滚、审计

## 8. 需要优先整改的点

### 8.1 快照模型要从“最新状态”收敛为“历史快照”

当前 `config_center` 已经提供时间线、版本对比、快照回看等产品语义，因此核心对象必须是“历史快照”，而不是“按设备覆盖更新的最新状态记录”。

整改目标：

- 每次配置采集生成独立快照
- 每个快照拥有独立主键、时间、文件路径、内容摘要
- 最新状态视图通过查询或派生表生成，而不是覆盖主表

### 8.2 合规结果要强绑定快照

合规结果不应仅按设备和规则覆盖更新，而应以“某次快照 + 某条规则”的方式持久化。

整改目标：

- 结果主键语义绑定 `config_backup_id + rule_id`
- 支持回看任意历史快照的合规状态
- 支持按快照对比合规变化

### 8.3 结构化结果与漂移结果要围绕快照闭环

结构化结果、漂移结果和策略命中都应围绕快照闭环组织。

整改目标：

- 某次快照对应一个结构化文档
- 某次快照与上一有效快照形成一个漂移文档
- 策略命中和审计记录可回溯到具体快照

### 8.4 工具接口与产品接口分层

当前调试工具型接口不应继续和产品主接口并列扩张。

整改目标：

- 主产品 API 仅保留配置管理相关能力
- 调试能力迁移到内部后台或单独工具路由
- 默认权限提升到管理员级别

### 8.5 南向执行能力不再在 `config_center` 内继续扩张

后续如果新增新的设备配置采集、协议适配、配置下发能力，应优先进入 `device_api`，而不是继续在 `config_center` 内新增直连执行逻辑。

整改目标：

- `config_center` 新增需求默认优先复用 `device_api`
- `config_center` 不再新增新的协议执行器和厂商连接逻辑
- 存量直连逻辑逐步替换或封装为兼容层

## 9. 分阶段计划

### P1：边界冻结与模型收敛

目标：

- 冻结产品边界
- 停止新增与 `device_api` 重合的功能
- 明确快照、合规、结构化、漂移的主数据模型

产出：

- 边界文档定版
- `config_center` 对外能力清单定版
- 快照模型和合规结果模型调整方案
- 工具接口清单和迁移清单

完成标准：

- 新增需求评审时可明确判定应进入 `device_api` 还是 `config_center`
- 配置快照成为 `config_center` 的统一核心对象

### P2：产品接口收敛与治理能力加强

目标：

- 按配置管理产品语义重组接口
- 清理工具型接口对主产品面的干扰
- 补齐权限和审计边界

产出：

- 配置快照、版本、合规、漂移四类主接口
- 调试工具路由下沉
- 策略管理和审计界面收敛

完成标准：

- 主接口不再直接暴露底层 Git、模板调试、文件树调试语义
- 角色权限可区分只读、治理、策略管理和管理员

### P3：与 `device_api` 协同收口

目标：

- 让 `config_center` 彻底从“直连执行者”收敛为“配置治理者”
- 让 `device_api` 成为设备侧采集和下发的唯一抽象入口

产出：

- `config_center` 对 `device_api` 的输入合同
- 存量配置备份任务的兼容迁移方案
- 配置采集事件或快照接入方案

完成标准：

- 新增配置采集执行能力统一落在 `device_api`
- `config_center` 只承接配置对象的管理与治理

## 10. 后续需求归属判断规则

后续新增需求可按以下规则判断归属：

如果需求核心问题是：

- 如何连接设备
- 如何做多厂商适配
- 如何做采集执行编排
- 如何做协议 fallback
- 如何做配置下发执行

归属 `device_api`。

如果需求核心问题是：

- 配置怎么存档
- 配置怎么回看
- 配置怎么比较
- 配置是否合规
- 配置是否漂移
- 配置风险如何分级
- 配置治理动作如何留痕

归属 `config_center`。

## 11. 一句话边界定义

`device_api` 面向设备，解决“采什么、怎么采、怎么下发、怎么抽象”。

`config_center` 面向配置，解决“怎么存、怎么看、怎么比、怎么管、怎么审计”。
