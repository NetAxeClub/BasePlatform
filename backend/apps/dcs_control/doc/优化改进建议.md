# DCS Control 模块优化改进建议

> 分析时间：2026-03-02
> 模块路径：`backend/apps/dcs_control/`
> 模块定位：防火墙统一纳管（DCS 控制器），支持山石（Hillstone）、华三（H3C）、华为（Huawei）三大厂商

---

## 一、现有功能架构梳理

```
dcs_control/
├── urls.py            # 路由定义（5个接口）
├── views.py           # 视图层（DRF APIView）
├── tasks.py           # Celery 异步任务 + 核心业务逻辑（~7000行）

```

### 核心功能对应关系

| URL | View 类 | Celery Task | 支持厂商 |
|-----|---------|-------------|---------|
| `deny_key/` | `DenyByAddrObj` | `bulk_deny_by_address` | Hillstone/H3C/Huawei |
| `address_set/` | `AddressSet` | `address_set` | Hillstone/H3C/Huawei |
| `service_set/` | `ServiceSet` | （同 address_set 内部分发） | Hillstone/H3C/Huawei |

| `sec_policy/` | `SecPolicy` | `config_sec_policy` | Hillstone/H3C/Huawei |

### 核心类结构

- **`FirewallMain`**：主业务类，封装多厂商登录信息获取、命令生成、流程引擎调度
- **`SecFirewallMain`**：安全策略专用类（Netmiko SSH 方式）
- **`SecPolicyMain`**：安全策略数据采集类
- **`CompareTwoDict`**：字典差异比较工具类
- **`WebSocket`**：WebSocket 推送装饰器

## 二、问题分析

### 2.1 严重问题

#### P0：存在安全隐患的硬编码逻辑

**位置**：`tasks.py` 第 216 行

```python
def sec_callback(flow_record_id):
    flow_record = AutoFlow.objects.filter(id=flow_record_id).values().first()
    if flow_record['commit_user'] == 'sbzhang7':   # ← 硬编码用户名
        url = "http://sparta.iflytek.com/api/work/info/update_dnat_id.action"
        response = requests.post(url, data=flow_record)  # ← 明文 HTTP 回调
```

**问题**：
- 硬编码特定用户名判断，不可维护，且每次操作都会走这个回调检查
- 使用明文 HTTP 而非 HTTPS
- 没有对 `response` 的异常处理，回调失败会导致静默错误

**建议**：将回调逻辑提取为可配置的 webhook，或通过数据库存储回调规则。

---

#### P0：`eval()` 执行用户数据

**位置**：`tasks.py` 第 7047 行

```python
try:
    host_vars = json.loads(host['ans_group_hosts__ans_vars'])
except Exception as e:
    b = eval(host['ans_group_hosts__ans_vars'])  # ← 极度危险
    host_vars = json.loads(b)
```

**问题**：`eval()` 会执行任意 Python 代码，如果数据库数据被污染或人为篡改，可导致 RCE（远程代码执行）。

**建议**：去除 `eval()`，改用 `ast.literal_eval()` 或在数据入库时确保格式正确。

```python
import ast
try:
    host_vars = json.loads(host['ans_group_hosts__ans_vars'])
except (json.JSONDecodeError, TypeError):
    host_vars = ast.literal_eval(host['ans_group_hosts__ans_vars'])
```

### 2.2 架构问题

#### P1：tasks.py 文件体积过大，违反单一职责原则

`tasks.py` 当前约 **7100 行**，包含：
- 工具函数（WebSocket 推送、设备锁、字典比较）
- 多厂商配置命令生成逻辑（Hillstone/H3C/Huawei 各自 CRUD）
- Celery Task 定义
- 数据采集逻辑

**建议**：按职责拆分为多个模块：

```
tasks/
├── __init__.py         # 对外暴露 Celery Task
├── celery_tasks.py     # Celery Task 定义（bulk_deny、address_set 等）
├── device_lock.py      # 设备锁管理
├── flow_engine.py      # 流程引擎（AutoFlow 操作、TTP 解析）
├── ws_notify.py        # WebSocket 通知
└── firewall/
    ├── __init__.py
    ├── base.py         # FirewallMain 抽象基类
    ├── hillstone.py    # 山石配置命令生成
    ├── h3c.py          # 华三配置命令生成（Netconf XML）
    └── huawei.py       # 华为配置命令生成（Netconf XML）
```

---

#### P1：多厂商逻辑通过 if/elif 链实现，扩展性差

**当前模式**：
```python
if vendor == 'Hillstone':
    cmds = self.hillstone_address_detail(...)
elif vendor == 'H3C':
    res, oms, back_oms = self.h3c_address_detail(...)
elif vendor == 'Huawei':
    oms, back_oms = self.huawei_address_detail(...)
```

**问题**：每增加一个新厂商，需要修改多处 if/elif，违反开闭原则。

**建议**：使用策略模式（Strategy Pattern），将厂商逻辑抽象为接口：

```python
from abc import ABC, abstractmethod

class FirewallAdapter(ABC):
    """防火墙适配器基类"""

    @abstractmethod
    def build_address_add_cmds(self, **kwargs) -> tuple:
        """生成地址对象新增命令和回退命令"""

    @abstractmethod
    def build_address_del_cmds(self, **kwargs) -> tuple:
        """生成地址对象删除命令和回退命令"""

    @abstractmethod
    def build_dnat_cmds(self, **kwargs) -> tuple:
        """生成 DNAT 命令和回退命令"""

    @abstractmethod
    def build_sec_policy_cmds(self, **kwargs) -> tuple:
        """生成安全策略命令和回退命令"""


class HillstoneAdapter(FirewallAdapter):
    def build_address_add_cmds(self, **kwargs) -> tuple: ...

class H3CAdapter(FirewallAdapter):
    def build_address_add_cmds(self, **kwargs) -> tuple: ...

class HuaweiAdapter(FirewallAdapter):
    def build_address_add_cmds(self, **kwargs) -> tuple: ...


# 注册表
ADAPTER_MAP = {
    'Hillstone': HillstoneAdapter,
    'H3C': H3CAdapter,
    'Huawei': HuaweiAdapter,
}

def get_adapter(vendor: str) -> FirewallAdapter:
    cls = ADAPTER_MAP.get(vendor)
    if not cls:
        raise ValueError(f"不支持的厂商: {vendor}")
    return cls()
```

#### P1：设备锁实现存在竞态条件

**当前实现**：
```python
def run_cmd_config(*cmds, **dev_info):
    count = 0
    while True:
        if not cache.get('automation_' + dev_info['ip']):
            cache.set('automation_' + dev_info['ip'], '1')  # ← 非原子操作
            ...
        else:
            count += 1
            if count > 3:
                break
            time.sleep(30)  # ← 阻塞 Worker 线程
```

**问题**：
1. `cache.get` 和 `cache.set` 不是原子操作，高并发下可能出现多个任务同时通过检查
2. `time.sleep(30)` 阻塞 Celery Worker，浪费资源
3. 最多等待 90 秒，对于长任务不够灵活

**建议**：使用 Redis 原子锁（`cache.add` 或 `django-redis` 的 `lock`）：

```python
from django.core.cache import cache

def run_cmd_config(*cmds, **dev_info):
    lock_key = f'device_lock_{dev_info["ip"]}'
    # cache.add 是原子操作：key 不存在时才设置，返回 True/False
    acquired = cache.add(lock_key, '1', timeout=300)  # 5分钟超时
    if not acquired:
        raise DeviceBusyError(f"设备 {dev_info['ip']} 正在被操作，请稍后重试")
    try:
        return BatManMain.hillstone_config_v2(*cmds, **dev_info)
    finally:
        cache.delete(lock_key)
```

对于需要等待的场景，可在 Celery Task 层面使用 ETA 延迟重试，而非在底层 sleep。

### 2.3 代码质量问题

#### P2：TTP 解析错误处理逻辑大量重复

在 `flow_engine`（`SecFirewallMain`）和 `flow_engine`（`FirewallMain`）中，TTP 错误解析代码完全相同，约 40 行重复。

**建议**：提取为独立函数：

```python
def parse_ttp_errors(ttp_res: dict) -> tuple[bool, str]:
    """
    解析 TTP 结果，返回 (is_failed, error_message)
    """
    for error_key in ['unrecognized', 'incomplete', 'errors', 'warning', 'wrong_parameter']:
        if error_key in ttp_res:
            msg = _extract_ttp_msg(ttp_res, error_key)
            return True, msg
    return False, ''
```

### 2.4 性能问题

#### P2：每次操作均创建新的 Netconf 会话

在 `h3c_address_detail` 的 `remove` 方法和 `h3c_service_detail` 的 `edit_object` 方法中，会在函数内部创建 `H3CSecPath` 连接用于查询，再调 `device.closed()`，之后在 `run_netconf_config` 中又会创建新连接执行配置下发。

**问题**：一次操作建立了 2 次连接，增加延迟，且在高并发场景下增加设备负担。

**建议**：将查询和配置下发合并到同一个连接会话中，或通过连接池复用连接。

---

#### P3：一键封堵（bulk_deny）串行调度

`bulk_deny_by_address` 对每台设备逐一调用 `address_set.apply_async`，但没有利用 `group` 或 `chord` 并行调度。

**建议**：使用 Celery `group` 实现真正的并行封堵：

```python
from celery import group

tasks = [
    address_set.s(**post_data_for_host)
    for post_data_for_host in all_host_data
]
job = group(tasks)
result = job.apply_async(queue=CELERY_QUEUE)
```

### 2.5 可维护性问题

#### P2：FirewallMain 和 SecFirewallMain 职责重叠

两个类都处理设备登录信息获取、命令下发流程，但一个用于安全对象操作，一个用于安全策略，代码逻辑高度相似，应合并或通过继承复用。

---

#### P2：models.py 空白，业务数据全部依赖 MongoDB

当前模块没有任何 Django 模型，流程记录依赖 `apps.automation.models.AutoFlow`，业务数据（地址对象、DNAT 记录等）存储在 MongoDB 中。

**问题**：关系型数据（如操作记录、审计日志）更适合存储在关系数据库中，当前架构使审计查询困难。

**建议**：考虑为以下数据建立 Django 模型：
- 封堵记录（`BlockRecord`）：记录封堵的 IP、操作人、时间、状态
- DNAT 发布记录（`DnatRecord`）：记录公网发布的详情，便于快速查询当前生效策略

---

#### P3：get_firewall_zone 厂商判断用别名不一致

```python
def get_firewall_zone(**kwargs):
    vendor = kwargs['vendor']
    if vendor == "Hillstone":   # 首字母大写
        ...
    elif vendor == 'H3C':       # 全大写
        ...
    elif vendor == 'Huawei':    # 首字母大写
        ...
```

而在 views.py 中某些接口支持的厂商列表是：`['hillstone', 'h3c', 'huawei']`（全小写），不同接口的厂商标识大小写不统一，容易出错。

**建议**：统一厂商标识规范，建议使用枚举类：

```python
from enum import Enum

class Vendor(str, Enum):
    HILLSTONE = 'Hillstone'
    H3C = 'H3C'
    HUAWEI = 'Huawei'
```

### 4.1 修复 eval() 安全问题

```python
# tasks.py bulk_deny_by_address 函数内

import ast

if host['ans_group_hosts__ans_vars']:
    try:
```

### 4.2 原子设备锁

```python
# 新建 device_lock.py

from contextlib import contextmanager
from django.core.cache import cache


class DeviceBusyError(Exception):
    pass


@contextmanager
def device_lock(ip: str, timeout: int = 300):
    """
    原子设备锁，确保同一设备同时只有一个任务执行。
    timeout: 锁最长持有时间（秒），防止死锁
    """
    lock_key = f'device_lock_{ip}'
    acquired = cache.add(lock_key, '1', timeout=timeout)
    if not acquired:
        raise DeviceBusyError(f"设备 {ip} 正在被操作，请稍后重试")
    try:
        yield
    finally:
        cache.delete(lock_key)


# 使用示例
def run_cmd_config(*cmds, **dev_info):
    with device_lock(dev_info['ip']):
        return BatManMain.hillstone_config_v2(*cmds, **dev_info)
```

### 4.3 提取 TTP 错误解析

```python
# 新建 flow_engine.py

def extract_ttp_error(ttp_res: dict) -> str:
    """从 TTP 解析结果中提取错误信息"""
    if 'unrecognized' in ttp_res:
        val = ttp_res['unrecognized']
        if isinstance(val, dict):
            return 'unrecognized: ' + str(val.get('unrecognized', ''))
        elif isinstance(val, list):
            return 'unrecognized: ' + '\n'.join(x['unrecognized'] for x in val)
    if 'incomplete' in ttp_res:
        val = ttp_res['incomplete']
        return 'incomplete: ' + (val.get('incomplete', '') if isinstance(val, dict)
                                 else '\n'.join(x['incomplete'] for x in val))
    if 'errors' in ttp_res:
        val = ttp_res['errors']
        if isinstance(val, dict):
            return 'error: ' + val.get('error', '')
        elif isinstance(val, list):
            return 'error: ' + '\n'.join(set(x['error'] for x in val))
    if 'warning' in ttp_res:
        return 'warning: ' + str(ttp_res.get('warning', ''))
    if 'wrong_parameter' in ttp_res:
        return 'wrong_parameter: ' + str(ttp_res['wrong_parameter'].get('wrong_parameter', ''))
    return ''
```

## 五、总结

| 维度 | 当前状态 | 主要风险 |
|------|---------|---------|
| 安全 | 存在 `eval()` 和硬编码回调 | RCE 风险、不可维护 |
| 架构 | 单文件 7000 行，逻辑高度耦合 | 新功能开发困难，测试覆盖难 |
| 并发安全 | 设备锁非原子，存在竞态 | 并发操作可能造成配置冲突 |
| 可扩展性 | if/elif 多厂商分支 | 新厂商接入成本高 |
| 可观测性 | print 混用，无结构化日志 | 生产问题排查困难 |
| 数据一致性 | 回退命令依赖 MongoDB 实时查询 | MongoDB 数据不一致时回退失败 |

建议优先解决 P0 安全问题，再逐步推进架构优化，每阶段改造应保证功能回归测试通过后再合并。
